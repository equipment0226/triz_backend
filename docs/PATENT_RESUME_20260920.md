# 특허 적재 복구·과학효과 검토 재개 — 2026-09-20

기존 BigQuery `tabledata.list` → MySQL 주요 필드 저장 → E5 임베딩 → Qdrant 적재 순서를 유지했다. SQL 검색 쿼리나 외부 LLM 추출로 바꾸지 않았다. 수집은 서버 `triz-patent-indexer`에서 채팅과 독립적으로 실행한다. 페이지 크기 1,000, 벡터 배치 64이며 기존 DB 200 GB·벡터 5천만 points 보호 한도도 유지한다. 원본 저장 범위는 기존과 같은 서지·제목·초록·분류이며 청구항·명세서 전문은 아니다.

## Crash 원인과 복구

- 정상 완료가 아닌 오류 종료였다. 원본 9,379,000행 순회, MySQL 6,665,951건, 벡터 처리 대기 0건에서 `source.complete=false`였다.
- Worker 로그는 `BadRequest`를 반복했다. 1행 진단에서 페이지 토큰의 읽기 시점 `2026-09-09T11:01:03.034Z`가 BigQuery의 읽기 허용 기간 밖으로 만료된 것을 확인했다. 같은 테이블 버전에서 `start_index=9379000`으로 1행 조회는 성공했다.
- `patent_ingest.source_pages`는 해당 만료 오류에 한해 원본 버전·행 수와 확정 체크포인트를 확인하고 확정된 `scanned` 위치로 재개한다. 다른 BadRequest나 원본 버전 변경에는 이 복구를 적용하지 않는다. 이후 페이지는 다시 정상 토큰으로 이어간다.
- 페이지 데이터와 체크포인트의 동일 트랜잭션 저장, 문서 해시 기반 중복 방지, Qdrant 성공 후 DB 확인 처리는 그대로다.
- 최초 복구 배포 `fa30191a-44d9-428c-b753-8e8f7855b5fc`에서 `RESUME_EXPIRED_TOKEN` 후 `IMPORT` 진행을 확인했다. Qdrant 절전 복귀 중 1차 연결 실패는 기존 재시도로 회복했다.
- 특허 Worker·Qdrant의 `sleepApplication=false`를 저장하고 기존 이미지로 재기동했다. Qdrant `7077917c-4eeb-45c0-9c8d-2f0a505250a6`, Worker `89f092cc-0b5e-4918-acf6-ea457c603020`. 기존 볼륨·컬렉션을 보존했다.

관측 증빙은 `.deployment/patent-diagnosis-20260920.json`, `patent-runtime-20260920-*.json`, `patent-services-20260920.json`이다. 수집은 전체 완료 또는 기존 용량·오류 보호조건까지 계속되며, 이후 새 원본 버전 정기 실행 스케줄을 추가한 것은 아니다.

## 기존 직접 추론 검토

과학효과는 `conversation_only` / `external_llm_calls_allowed=false`를 유지했다. 저장 초록 200건(`AR-033572-A1`~`AR-037254-A1`)을 직접 읽어 LINK 64, DEFER 72, DESIGN_ONLY 64건을 기록했다. 프로그램은 판단 생성 없이 유효한 정본 키·입력 해시를 검사하고 저장·발행만 수행한다.

누적 조회 1,720건, 직접검토 초록 1,272건, 초록 없음 448건, 미검토 0건. 정본 19개 기능군·269개 효과를 유지하며 64개 특허의 출처를 보강했다. 전체 특허 순회는 미완료다. 기존 자동 추출 스크립트 `effect_worker.py`, `sweep_patent_effects.py`, `refresh_effects.py`는 실행하지 않았다.

결정 TSV·불변 검토·출처 원장·로컬 serving JSON을 저장했다. 이번 과학효과 출처 갱신은 운영 백엔드 이미지에 아직 배포하지 않았다. 다음 검토는 `next-request.json`의 `AR-037254-A1` 이후를 `page-000012.json`으로 조회한다. 11페이지 원문은 `manual_archives/2026-09-20-01.json.gz`에 백업하고 복원 일치를 확인했다.
