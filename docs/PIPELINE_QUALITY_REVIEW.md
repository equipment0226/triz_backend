# 추론 파이프라인 품질 분석

분석일: 2026-09-09. 대상: `pilot/triz/`, `pilot/config/`, 관련 테스트.

현재 구조는 여러 TRIZ 기법으로 후보를 넓히고 보고서까지 완주하는 데 강점이 있다. 어려운 문제의 품질을 제한하는 주요 원인은 **문제 유형과 산업의 혼동, 단계 사이의 근거 손실, 수량·형식 중심의 완료 조건, 검증 결과가 다음 설계를 충분히 바꾸지 못하는 구조**다. 모델 호출을 무조건 늘리기보다 이 네 부분을 먼저 고치는 것이 적절하다.

이 문서는 변경 전 상태의 분석 기록이다. 이후 코드·프롬프트·설정에 반영한 내용과 검증 범위는 [반영 내역](PIPELINE_QUALITY_IMPLEMENTATION.md)에 정리했다. 아래의 지연 효과는 실행 의존관계에 근거한 예상이며, 동일 문제를 사용한 변경 전후 측정 결과가 아니다.

## 1. 실제 실행 구조

실행 순서는 [pipeline.py](../pilot/triz/pipeline.py:15)에 정의되어 있다.

| 단계 | 실제 수행 | 품질상 의미 |
|---|---|---|
| S0 | 실행 모드·공학 여부 판단 | 최초 분류. 모드에 따라 기본 트랙이 결정됨 |
| S0_RESEARCH | 키워드 산업 분류 → 이론·경쟁 가설 생성 → 사용자 질문 | 심층 검토가 있지만 산업과 문제 유형이 별도 기준 없이 혼재 |
| S1 | 원문·첨부·응답에서 문제와 제약 추출 | 도메인 객체를 다시 만들며 최초 공학 여부를 대체 |
| S2 | 시스템 경계 후보 → 사용자 선택 | 선택 결과가 모든 후속 노드에 일관되게 반영되지는 않음 |
| S3 | 9-Windows → 기능 모델 → 자원·CECA·Su-Field 병렬 → 내재 제약 | 원인 분석의 중심. 비기술 문제에도 물질·장 관점이 유입됨 |
| S4 | IFR → 모순 → 트리밍 → 핵심 문제 | 현재 순차 실행. 깊은 인과관계가 텍스트 요약으로 축소됨 |
| S5 | 모드별 트랙 병렬 → 사전 검색 → 통합 → 부족 시 추가 트랙 | 폭넓은 탐색. 심화 기준은 주로 수량·범주 충족 |
| S6 | 5개씩 최대 3배치 순차 개념화 | 첫 배치만 독립 검증. 기본 최대 12개인데 최대 15개 생성 후 절단 |
| S7 | 개념·제약을 작은 배치로 순차 판정 | 제약 준수 검사이며 모순 해소의 깊이를 보장하지 않음 |
| S8 | 페르소나 생성 → 병렬 평가 → 순위 | 실행성·비용 비중이 크고 목표 달성·모순 해소가 별도 축이 아님 |
| References / S9 | 상세 검색·근거 연결 → 보고서 | 상세 적용성 검토가 주요 개념 생성·평가 뒤에 위치 |
| S10 | 피드백 정제 → 로컬 RAG 적재 | 정제한 교훈 대부분이 실제 검색·생성 경로에 연결되지 않음 |

유지할 장점도 명확하다. TRIZ 지식의 로컬 카탈로그, 트랙 출력의 격리와 결정적 병합, 검색 실패와 검색 결과 없음의 구분, 제약 게이트, 사용자 판단 뒤에도 조건부 상태를 유지하는 처리, 호출 기록·캐시가 이미 있다. 이 기반을 활용하면 전면 재작성 없이 개선할 수 있다.

## 2. 우선순위가 가장 높은 발견

### P0-1. 비즈니스 분기가 있어도 공학 프레임이 다시 덮인다

근거:

- [domain.py](../pilot/triz/domain.py:10)의 산업 분류는 키워드 일치 개수의 최댓값이다. 동점이면 카탈로그 순서가 영향을 준다.
- [industries.yaml](../pilot/config/industries.yaml:51)은 business/general을 기본 `routine`, 깊이를 `component`로 설정한다. 조직·인센티브 문제의 복잡성이 산업 이름과 독립적으로 평가되지 않는다.
- [domain.py](../pilot/triz/domain.py:43)는 모든 후속 도메인 컨텍스트에 “관련 물리·화학·공학 이론”을 검토하라는 문장을 붙인다. `is_engineering=false`도 예외가 아니다.
- [P_S1_EXTRACT.md](../pilot/triz/prompts/P_S1_EXTRACT.md:1)는 모듈·진공·하중·기술 키워드를 중심으로 추출을 유도한다.
- [P_S5_TRACK_G.md](../pilot/triz/prompts/P_S5_TRACK_G.md:1)는 일반화 기능을 반드시 “물리적 동작”으로 바꾸도록 한다.
- [P_S5_TRACK_H.md](../pilot/triz/prompts/P_S5_TRACK_H.md:1)는 물리·화학·기하학적 효과를 요구한다. FULL에서도 기본 활성화된다.
- [P_S6_CONCEPT.md](../pilot/triz/prompts/P_S6_CONCEPT.md:1)는 기술 명칭, 부품·공정 변경, 물리 법칙/효과를 요구한다.
- S4의 `BIZ_31` 분기는 존재하지만 S3 Su-Field 및 S5 C/H의 적용성 판단은 해결하지 못한다. S5는 Su-Field가 있으면 C를 추가하기도 한다.

오프라인으로 재현한 분류:

| 입력 | 현재 산업 / 난이도 |
|---|---|
| 조직에서 성과급을 높일수록 협업이 줄고 부서 간 지식 공유가 감소한다 | business / routine |
| 반도체 회사의 조직에서 성과급을 높일수록 협업이 줄고 지식 공유가 감소한다 | semiconductor / frontier |
| 구성원의 자율성과 책임을 동시에 높이는 인사평가 제도를 만들고 싶다 | general / routine |

이는 최종 LLM 출력의 오분류율 측정이 아니라, **분석을 유도하는 라우터의 동작 재현**이다. business로 분류한 상태에서도 공학 지시가 붙는 것도 확인했다.

개선:

1. 기존 S0 또는 S1 호출에서 `industry`와 별도로 `problem_type`을 판정한다. 예: `PHYSICAL_TECHNICAL`, `INFORMATION_SOFTWARE`, `ORGANIZATIONAL_BUSINESS`, `MIXED`. 새 분류 호출은 추가하지 않는다.
2. `difficulty`는 산업이 아니라 관측 부족, 경쟁 가설, 이해관계 충돌, 원인 연결의 복잡성, 기존 실패 이력으로 정한다. 정보 부족을 단순함으로 해석하지 않는다.
3. 공통 컨텍스트·트랙 선택·용어 사전·평가 역할이 동일한 문제 유형을 사용하게 한다. 키워드 분류는 잠정 힌트로만 남긴다.
4. 비기술 문제에서 C/H를 무조건 실행하지 않는다. A/B/E 및 도메인에 맞게 수정한 F/G를 우선한다. 혼합 문제는 물리 하위문제에만 Su-Field/Effects를 적용한다.
5. 조직 문제에서는 기능의 주체를 사람·팀·규칙·정보·의사결정 권한으로, 작용을 승인·보상·공유·협상·선택으로 기술한다. 관측 없이 심리 상태를 사실로 단정하지 않는다.

권장 공통 지시의 예:

> 산업 배경과 해결할 문제의 작동 방식을 구분하라. 비기술 문제는 행위자·정보·권한·유인·제도 간 관계로 설명한다. 원문에 없는 센서·장치·재료를 도입해 문제를 재해석하지 않는다. 물리적 모순을 적용한다면 동일 행위자/규칙의 동일 속성에 걸린 상반 요구를 명시하고, 성립하지 않으면 적용 불가로 기록한다.

효과 예상: 추가 호출 없이 편향 감소. 부적합 트랙을 제외하는 경우 호출·출력량도 줄어든다.

### P0-2. 비용을 들여 만든 깊은 분석이 S5 → S6에서 사라진다

[digest.py](../pilot/triz/digest.py:82)의 현재 전달 내용:

- 기술적 모순: 조치, 개선/악화 **번호**, 라벨. `then_good`, `but_bad`, 매핑 근거와 파라미터 체계가 생략된다.
- 물리적 모순: 요소·파라미터·두 상태. 각 상태가 필요한 이유, 연결된 기술적 모순, 분리 후보가 생략된다.
- 아이디어: ID·트랙·출처·제목·본문만 전달한다. `detail`의 자기 반박, 적용 조건, 이식 주의점, 새로운 위험 및 구조화된 모순 연결은 빠진다.
- CECA 씨앗은 노드의 문장만 전달한다. 부모 관계, AND/OR, 검증 방법이 떨어져 나간다.

실제로 `RawIdea.detail`에 넣은 조건·이식 주의점이 `ideas_digest()` 결과에 없는 것을 재현했다. 원본 데이터는 저장되지만 후속 추론 입력에 없다는 뜻이다. 공통 `deep_dive` 요약은 계속 제공되므로 전체 맥락이 모두 없어지는 것은 아니다. **각 후보에 고유한 근거**가 사라지는 것이 핵심이다.

통합 단계도 병합된 여러 아이디어 중 첫 번째 원본의 `detail`만 유지한다. 트랙 순서대로 모은 아이디어를 첫 60개까지만 전달하므로 후보가 많으면 뒤쪽 F/G/H의 탐색 결과가 입력에서 잘릴 수 있다.

개선:

- `contradiction_packet`: ID, 자연어 개선/악화 목표, 각각 필요한 이유, 결합 원인, 적용 범위, 근거/가설 구분.
- `idea_packet`: ID, 해소할 모순, 개입 변수, 작동 메커니즘, 필요 조건, 가장 강한 반박, 자원, 검증 방법.
- 전체 산출물을 붙이지 말고 핵심 문제에 연결된 인과 경로와 후보별 핵심 필드만 전달한다. 원문 설명의 반복을 줄여 입력 예산을 맞춘다.
- 병합 시 모든 `source_idea_ids`와 필수 조건을 보존한다. 상충하는 조건은 숨기지 않고 미해결로 표시한다.
- 60개 제한은 단순 앞부분 자르기 대신 핵심 문제·작동 방식별 대표 후보 선정으로 바꾼다.

프롬프트에 새 필드만 추가하면 `coerce.build()`가 스키마에 없는 필드를 버린다. **프롬프트·스키마·digest·소비 노드를 함께 수정해야 한다.**

효과 예상: 추가 호출 0. 토큰 증가 가능성이 있으므로 전체 컨텍스트 길이를 고정하고 중복 설명을 대체하는 방식으로 적용한다.

### P0-3. ‘개념 개수와 분류의 다양성’이 ‘모순 해소의 깊이’를 대체한다

[P_S5_MERGE.md](../pilot/triz/prompts/P_S5_MERGE.md:1)의 보강 기준은 12개 이상, 핵심 문제마다 2개, 3종 이상의 트랙, 신규성 3종, 계층 다양성이다. 따라서 개수만 보는 것은 아니지만, **인과 타당성·상반 요구의 동시 충족을 직접 검증하는 기준이 부족하다.**

[nodes.py](../pilot/triz/nodes.py:815)의 심화는 통합의 `need_more`와 수량을 이용해 아직 실행하지 않은 트랙을 추가한다. DEEP에서 모든 트랙을 이미 사용했다면 추가 목록이 비어도 다시 통합할 수 있다. 설정의 `ariz.max_reformulation_loops`는 실행 코드에 연결되어 있지 않다.

ARIZ Part7에서 절충으로 판정한 안은 경고만 기록한다. 해당 원시 아이디어를 직접 제외하거나 수정하지 않는다. B 트랙의 `redefine_hint`도 문제 재정의 제어에 사용되지 않는다.

개선:

- 기존 S5 통합에서 각 후보를 `RESOLVED`, `TRADEOFF`, `UNSUPPORTED`로 구분한다. 이는 제안하는 제품 내부 분류이며 정식 TRIZ 용어를 새로 주장하는 것이 아니다.
- 판정 근거는 “무엇을 바꾸면 A가 좋아지고, 기존에 함께 나빠지던 B는 어떤 구조 때문에 유지되는가”로 통일한다.
- 주요 가설이 틀릴 때도 성립하는지, 어떤 관측으로 반증할 수 있는지 기록한다.
- 같은 모순·같은 개입 변수·같은 메커니즘을 쓰는 후보는 제목이 달라도 같은 계열로 센다.
- `need_more`는 핵심 모순의 미해결·부적합 근거·단일 가설 의존성으로 판단한다. 이미 많은 후보가 있으면 확장 대신 약한 후보를 교체한다.
- 엄격한 시간 제한에서는 기존 호출 안에서 대안 가설과 반례를 점검한다. 별도 재정의 호출이 필요한 경우에는 기존 트랙/개념화 호출 예산을 대체하며, 재정의가 선행 모델을 무효화한다면 영향받은 산출물도 갱신한다.

“더 깊게 생각하라” 대신 넣을 지시:

> 후보마다 결합 원인과 개입 변수를 명시하라. 개선 목표의 달성 경로와 악화 목표의 보존 경로를 각각 설명하라. 원래 손실을 다른 행위자·시점·부서로 이전했을 뿐이면 해소로 분류하지 않는다. 가장 강한 실패 가설과 이를 구분할 관측을 적고, 설명할 수 없는 후보는 개수 목표 때문에 남기지 않는다.

### P0-4. 검증기의 입력과 검증 범위가 품질 목표에 부족하다

[agent.py](../pilot/triz/agent.py:73), [nodes.py](../pilot/triz/nodes.py:948), [rubrics.yaml](../pilot/config/rubrics.yaml:1)에서 확인했다.

- 독립 검증은 `critical_rubrics` 4종만 실제 실행한다. S5 통합 및 트랙의 대부분은 독립 의미 검증을 받지 않는다.
- R3_FUNC는 재진술만, R3_CECA는 증상만 사실로 받는다. 사용자 응답·첨부·기존 실패를 포괄하는 사실 입력이 아니다.
- R4_CONTRA는 파라미터 정의와 정확한 매핑, 원문·인과사슬에서의 도출 여부를 평가해야 하지만 검증기에는 문제 기능 요약만 준다. 파라미터 정의 사전도 없다.
- S6는 첫 배치에만 R6_CONCEPT를 실행하고 `facts`를 전달하지 않는다. 기본 12개 중 뒤 7개에는 같은 독립 심사가 없다.
- 검증기는 “사실 근거 밖의 사실은 없다고 간주”하라고 지시받는다. 빈 사실 입력은 올바른 설계 가정과 근거 없는 단정을 구분하기 어렵게 만든다.
- REJECT/REVISE가 수리 상한에 도달하면 `WARN`으로 산출물을 반환한다. 치명적 결함이 최종 추천에서 별도로 배제되는 보장은 없다.

개선:

1. 사용자 원문·첨부 관측·확인된 답변·성공 기준을 압축한 공통 사실 패킷을 만든다. 가설은 별도 목록으로 구분한다.
2. R4에는 사용된 파라미터 정의와 관련 CECA 경로를 제공한다. R6에는 대상 모순, 사실 패킷, 후보의 설계 근거를 제공한다. 생성기의 자기평가 점수는 주지 않는다.
3. S6 첫 배치 전용 심사를 전체 후보의 압축된 설계 근거 심사로 재배치하는 방안을 검토한다. 호출 수는 같게 유지할 수 있으나 전체 후보를 1,200 출력 토큰에 억지로 넣으면 다시 얕아지므로 항목 수·출력 형식을 함께 설계한다.
4. 문장·형식 오류와 치명적 사실/모순/제약 오류를 분리한다. 치명적 미해결 후보는 추천에서 제외하거나 검증 전 가설로 표시한다. 모든 경우를 무한 재시도하는 방식은 피한다.
5. S7의 실제 노드는 `s7_gate_1` 등인데 도메인 컨텍스트는 `node == "s7_gate"`만 격리한다. 접두사 기준으로 수정해야 한다. 실제로 접미사가 있는 노드에는 경쟁 가설이 그대로 전달됨을 재현했다.

효과 예상: 사실 패킷과 노드 조건 수정은 추가 호출 0. 심사 재배치는 호출 수를 유지할 수 있으나 수리율과 토큰을 함께 측정해야 한다.

### P0-5. 사용자가 확정한 문제 경계와 후속 분석 경계가 달라질 수 있다

[nodes.py](../pilot/triz/nodes.py:147)의 S2 재개는 선택 ID를 저장하지만 `st.domain.target_system`을 갱신하지 않는다. S3 기능 모델은 `confirm.chosen()`을 받는 반면 9-Windows와 다수 S5/S6 노드는 기존 `domain.target_system`을 받는다. 후보가 다른 시스템 경계를 의미하면 서로 다른 문제를 풀게 된다.

또한 S1 역질의가 반복되면 `st.intake.clarify_turns = turns`로 과거 질문·답변을 대체한다. S0 심층 답변은 별도 컨텍스트에 남지만 S1 자체의 누적 응답 이력은 보존되지 않는다.

개선: 확정된 시스템을 단일 기준으로 읽는 함수를 모든 노드에서 사용하고, 경계·작용 영역·시간·사용자 수정 사항을 함께 유지한다. 역질의는 이력을 누적하고 현재 미응답 묶음만 답변에 연결한다. 추가 호출 없이 정합성을 높일 수 있다.

## 4. S10 피드백은 어디까지 학습에 쓰이는가

[P_S10_FEEDBACK_DISTILL.md](../pilot/triz/prompts/P_S10_FEEDBACK_DISTILL.md:1)는 `accepted_patterns`, `rejected_patterns`, `domain_lesson`, `generalized_problem`을 만든다. 그러나 [rag.py](../pilot/triz/rag.py:54)의 적재에서 정제 결과 중 읽는 것은 `generalized_problem`뿐이다.

현재 성공 사례에는 개념의 working_principle 일부가 저장되고, 실패 사례에는 원문 코멘트와 reason_tags가 저장된다. 따라서 피드백이 전혀 활용되지 않는 것은 아니다. 다만 정제한 도메인 교훈과 실패의 일반화가 다음 실행에 직접 전달되지 않는다. S10 정제 호출에는 개념의 상세 작동 원리도 전달하지 않고 제목·점수·채택 여부·코멘트만 준다.

추가로 `is_engineering`은 성공 사례 메타데이터에 저장하지만 검색에서 필터/호환성 검사에 사용하지 않는다. 같은 문제 유형에서의 재사용인지 확인하지 않은 채 문자열 유사성과 산업 보너스로 뽑는다. RAG의 영향 개수 제한도 프롬프트 문장만으로 적용된다.

개선:

- 동일 S10 호출에 메커니즘과 실제 실패 조건을 넣는다. accepted/rejected/domain_lesson을 저장하고 관련 단계의 입력에 사용한다.
- 사용자의 선호·채택과 실제 성과 검증을 구분한다. 높은 별점만으로 효과가 검증된 사례라고 해석하지 않는다.
- 검색은 문제 유형, 모순 구조, 적용 조건의 호환성을 먼저 확인한다. 타산업 전이는 별도 표시하고 허용한다.
- S1/S3에는 관련 실패 교훈, S6에는 성공 메커니즘을 제한적으로 전달한다. 가설성 교훈을 절대 제약으로 승격하지 않는다.
- 이 변경에는 새로운 LLM 호출이 필요하지 않다. 현재 이미 지불하는 정제 호출의 활용도를 높이는 작업이다.

## 5. 분석 시간을 늘리지 않기 위한 실행 설계

권장 순서는 **입력 정합성 복구 → 불필요한 생성량 감축 → 의존성이 없는 작업 병렬화 → 남은 시간 안에서 심화**다.

| 변경 | 호출 수 | 시간에 관한 판단 |
|---|---:|---|
| 유형별 공통 지시·프롬프트·트랙 선택 | 동일 또는 감소 | 먼저 적용할 대상 |
| 확정 경계·질문 이력·구조화 digest·검증 사실 패킷 | 동일 | 중복 문장을 줄여 입력 토큰 예산 유지 |
| S5 통합의 완료 조건을 모순 해소 기준으로 변경 | 동일 | 수리/보강이 늘지 않도록 기존 호출 예산 안에서 후보 교체 |
| S6 마지막 배치를 `min(batch_size, target-len(concepts))`로 요청 | 동일 또는 감소 | 기본 12개 목표에서 최대 15개 생성 후 3개 버리는 낭비 방지 |
| S4 IFR·모순·트리밍 병렬화 후 핵심 문제 선정 | 동일 | 현재 입력상 앞 세 작업은 서로 산출물을 사용하지 않음. 상태 커밋은 순서 고정 필요 |
| S7 독립 배치 병렬화 | 동일 | 현재 6~12개 직렬 호출을 worker 제한 안에서 실행 가능. rate limit 및 예산 예약 보존 필요 |
| S6 후보를 사전 배정해 배치 병렬화 | 동일 | 현재는 이전 제목으로 중복을 피하므로 단순 병렬화 금지. 메커니즘별 배정 및 사후 중복 검사 선행 |
| S5 검색과 트랙의 겹쳐 실행 | 동일 | 현재 검색 입력에 트랙 결과가 포함되므로 그대로 병렬화 불가. 검색 계획을 사실·모순 기반으로 재설계해야 함 |
| 전체 검증 추가·DEEP 일괄 사용·모델 전면 교체 | 증가 가능 | 이번 목표의 첫 조치로 권장하지 않음 |

S4의 예상 구조 변화는 `T_IFR + T_CONTRA + T_TRIM + T_KEY`에서 `max(T_IFR, T_CONTRA, T_TRIM) + T_KEY`다. S7도 독립 배치의 직렬 합 대신 worker 수에 따른 실행 묶음으로 바뀐다. 실제 이득은 토큰 생성량·공급자 동시성·재시도에 달려 있으므로 초 단위 절감치를 단정할 수 없다.

로컬에서 로드한 현재 모델 설정은 T1/T2/T3 모두 `deepseek-chat`이며 출력 상한은 각각 2,000/4,000/8,000이다. T2는 역할 이름일 뿐 별도 고성능 모델이 자동 선택되는 구조가 아니다. S5 통합과 S6는 호출별로 8,000을 지정한다. 이 값은 로컬 설정 확인 결과이며 실제 배포 환경이 동일하다는 뜻은 아니다.

어려운 문제의 물리·조직 메커니즘에 관한 자료가 없으면 프롬프트만으로 검증된 해법을 보장할 수 없다. 이 경우의 품질은 임의로 구체화하는 대신 ‘어떤 가설에 의존하는 해법인지, 어떤 관측이 있어야 선택할 수 있는지’를 명확히 하는 데서 높아진다.

## 6. 권장 적용 묶음과 검증

첫 변경 묶음: P0-1 문제 유형 계약, P0-2 근거 전달, P0-4 검증 입력, P0-5 경계/응답 이력, CECA 순환 검사. 모두 추가 LLM 호출 없이 구현할 수 있는 변경이다. 유형별 프롬프트는 경영용 표현을 한 문장 덧붙이는 방식보다 기존 공학 예시와 강제 요구를 조건부로 교체해야 한다.

두 번째 묶음: S5 모순 해소 판정과 후보 배정, S6 생성량 조정, 검증 재배치, S4/S7 병렬화. 이때 후보 수를 많이 유지하는 것과 핵심 해법의 완성도를 구분한다. 사용자에게 보여줄 넓은 후보 목록과 상세 설계가 필요한 후보를 구분하는 제품 정책도 검토할 수 있다.

세 번째 묶음: 검색의 질문 중심 전환, 도메인별 평가·RAG 개선, 필요한 경우 선택적 모델 변경. 앞선 변경과 섞어 한 번에 비교하면 무엇이 품질을 바꿨는지 알기 어렵다.

품질 비교용 문제군은 단순 공학 / 고난도 공학 / 조직·사업 / 혼합 문제로 나눈다. 각 문제에는 같은 조건을 유지하면서 산업 배경만 바꾼 쌍을 포함한다. 예: 일반 회사의 보상·협업 문제와 반도체 회사의 동일 문제. 불충분한 관측, 명시된 실패 이력, 사용자가 두 번째 경계 후보를 선택하는 사례도 포함한다.

비교 지표:

- 도메인 충실성: 원문에 없는 물리 장치·공정을 핵심 원인이나 해결 수단으로 끌어왔는가.
- 모순 해소: 양쪽 요구의 성립 조건이 구체적인가. 단순 완화·손실 전가와 구분되는가.
- 인과 근거: 관측·가설이 구분되고 경쟁 설명을 판별할 수 있는가.
- 실행 가능성: 기술 문제는 변경 대상·작동 조건, 조직 문제는 행위자·규칙·권한·유인이 구체적인가.
- 검증 가능성: 기준 상태, 관측 방법, 실패 조건이 있는가.
- 다양성: 제목/트랙이 아니라 서로 다른 개입 메커니즘인가.
- 성능: 사용자 대기 시간을 제외한 전체 및 단계별 p50/p95, 호출 수, 입력/출력 토큰, 재시도·수리율.

평가자는 변경 버전을 모르는 상태에서 동일 문제의 결과를 비교한다. 소규모 파일럿으로 지표를 다듬고, p95는 충분한 반복 실행을 확보한 뒤 판단한다. “호출 수가 같다”는 것만으로 지연이 같다고 판정하지 않는다.
