# S8 다직군 회의 평가

S8은 각 직군이 독립 점수를 낸 뒤 실제로 다른 직군에 질문하고, 받은 답변을 검토해 최종 점수를 다시 낸다. 구현은 [meeting.py](../pilot/triz/meeting.py), 연결 지점은 [nodes.py](../pilot/triz/nodes.py)의 `s8_evaluate`다.

## 실행 순서

1. **독립 검토**: 모든 개념 × 담당 평가 차원의 최초 점수와, 다른 참가자에게 보낼 1차 질문을 만든다.
2. **1차 답변**: 질문의 실제 수신 직군이 자신의 전문 관점으로 답한다.
3. **2차 후속 질문**: 모든 1차 답변이 모인 뒤, 답변의 가정·실패 조건·미해결 쟁점을 다시 묻는다. 이전에 답변된 질문 ID와 같은 개념을 참조해야 한다.
4. **2차 답변**: 후속 질문의 수신 직군이 답한다.
5. **최종 검토**: 각 직군이 자신의 최초 평가와 실제 전체 문답을 읽고 최종 점수, 개선 제안, 소통 반영 요약을 반환한다. 이 점수만 집계·순위 산정에 사용한다.

각 순서 내부의 직군 호출은 병렬이다. 다음 순서는 현재 순서의 필수 응답이 모두 검증된 후 시작한다. 질문을 받지 않은 직군의 빈 답변 호출은 생략하지만, 모든 직군은 질문·후속 질문·최종 평가에 참여한다. 하나의 모델 응답이 여러 직군의 대화를 대신 작성하지 않는다.

## 최종 응답과 근거

각 직군은 제공된 개념별 문답 묶음의 `summary_id`를 선택하고, 소통 내용 `summary`, 최초 판단의 변경·유지 이유 `assessment_change`, 남은 쟁점 `unresolved_issues`를 작성한다. 서버가 해당 선택지의 실제 `concept_id`, `peer_role_ids`, `question_ids`를 연결해 저장한다. 직접 소통한 교환을 최소 한 건 요약해야 한다. 후속 질문도 `followup_id` 선택지를 통해 실제 이전 질문과 개념에 연결한다. 별도 회의록 보고서나 보고서 템플릿을 추가하지 않으며, 응답과 문답은 실행 상태·단계 기록에 보관한다.

평가자에게는 사용자 입력·답변·확인 사실, 개념의 작동 조건과 위험, 기존에 연결된 근거의 ID·본문 발췌·확인 여부·적용 범위를 제공한다. TRIZ 생성 경로와 경쟁 원인 가설은 평가자 컨텍스트에서 제외한다. 회의 중 새 검색은 수행하지 않는다. 동료의 주장이나 합의는 실증 근거로 취급하지 않고, 모르는 정보는 불확실성과 검증 방법으로 남긴다.

최종 점수가 모든 개념과 담당 차원을 빠짐없이 포함하는지, 숫자가 유효한지, 질문·수신자·근거·요약의 ID가 실제 기록과 일치하는지 코드로 검사한다. 형식이 맞는 것만으로 발언의 사실성이나 의미적 타당성이 보장되는 것은 아니다. 최종 평가는 기존 `R8_REVIEW` 연결을 유지하며, 검증이 활성화된 설정에서는 실제 문답과 근거도 검증기에 제공한다. 현재 기본 `critical_rubrics`에는 R8이 없어 별도 모델 검증 호출은 생략된다.

기존 점수 가중치와 제약 게이트 판정을 유지한다. 최초 검토에서 거부권 담당자가 명시한 실제 안전 veto(`SAFETY`, 1.5점 이하, 위험 명시)는 같은 근거만으로 진행한 회의에서 삭제할 수 없다. 일반 비용·일정상의 우려나 조건부 안전 평가는 구체적인 답변에 따라 수정할 수 있다. 소수 의견이나 미확인 위험을 합의만으로 해소하지 않도록 프롬프트에서도 지시한다.

## 중단·재개

`evaluation.meeting`에 최초 평가, 질문, 답변, 최종 직군 응답, 완료된 호출과 입력 해시를 저장한다. 참가자 ID는 같은 회의 입력으로 재시도할 때 유지한다. 문제·개념·근거·역할·라운드 조건이 달라지면 회의를 새로 구성한다. 출력 한도·형식 프롬프트만 바뀌면 현재 검증을 통과하는 완료 호출은 보존한다. 앞선 문답이 달라지면 단계별 입력 해시가 달라져 이전 후속 응답도 재사용하지 않는다. 기존 형식의 미완료 회의는 저장된 최초 호출의 입력·역할이 현재 값과 같을 때만 이어받는다.

호출이 실패하거나 응답 검증을 통과하지 못하면 완료된 직군의 결과를 저장하고 집계 전에 중단한다. 이어서 실행할 때 미완료 호출부터 재개한다. 참가자 구성 실패도 회의 시작 전에 중단한다. 순위 산정 호출이 실패하면 후보를 줄이지 않으므로, 재시도 시 완료된 회의를 재사용할 수 있다. 기존 파이프라인의 중단 상태·재시도 알림 경로를 따른다.

## 호출 수와 설정

[triz.yaml](../pilot/config/triz.yaml)의 기본값은 다음과 같다.

```yaml
evaluation:
  meeting_rounds: 2
  meeting_questions_per_role: 2
  meeting_review_max_tokens: 8000
  meeting_final_batch_rows: 12
  meeting_exchange_max_tokens: 4000
  meeting_repair_attempts: 2
```

라운드 수는 1~2, 직군당 한 라운드의 질문 수는 1~2로 제한한다. 2라운드일 때 직군 수를 N이라 하면 기본 평가·문답 생성은 최대 **5N회**다. 최종 평가는 개념 수 × 담당 차원이 12행을 넘으면 나누어 호출하므로 추가 호출이 발생한다. 각 호출은 전체 개념과 실제 문답을 보면서 지정된 개념만 평가하고, 소통 요약은 첫 호출에서 한 번 기록한다. 성공한 분할 응답도 저장해 실패한 부분만 재시도한다. 참가자 생성, 최종 평가 검증, 수리·재시도, 순위 산정 호출은 기본 호출 수에 포함하지 않는다.

질문은 핵심 쟁점 하나를 묻는 한 문장(120자 이내), 답변은 판단과 조건을 담은 1~2문장(220자 이내)을 목표로 한다. 길이 때문에 기존 내용을 잘라내거나 검증 실패를 만들지는 않으며, 실제 위험과 판단을 바꿀 조건은 유지하도록 프롬프트에서 지시한다.

최종 응답의 `concept_comments`는 개념별·직군별 한 문장 결론이다. 보고서와 해결책 카드는 동일한 코멘트를 사용하며, 차원별 중복 표와 막대를 표시하지 않는다. 기존 데이터는 저장된 판단·위험·소통 요약에서 주요 의견을 골라 직군당 한 행으로 표시한다. 상세 점수와 문답 원본은 유지하며 안전 veto를 낙관적 코멘트로 덮지 않는다. 다운로드도 현재 서식으로 렌더링한다.

`pilot/scripts/rerun_completed_reviews.py`는 명시한 완료 케이스의 S8과 S9만 다시 실행한다. 원본을 먼저 보관하고, 입력·해결책·사용자 피드백을 유지한다. 작업 ID별 완료 상태와 비용 기준점을 저장하며, 재시도에는 같은 한도와 완료 호출을 재사용한다. 한 번에 최대 2건을 실행한다.

기존 `s8_review` 접두사를 사용해 평가 모델 T3 및 컨텍스트 격리 정책을 유지한다. 최초·최종 평가의 출력 한도는 기본 8,000토큰, 문답은 기본 4,000토큰이며 받은 질문 수가 많으면 최대 8,000까지 늘어난다. 실제 답변이 끝나면 그 시점에 종료한다. 형식·참조 수리는 최대 2회이고, 수정 응답에서 빠진 기존 최상위 필드는 보존한 뒤 전체 응답을 다시 검사한다. 점수·근거·답변을 임의로 채우거나 존재하지 않는 대화로 오류를 덮지 않는다. 기존 공통 병렬 호출 제한, 실행 시간·비용 예산을 그대로 적용한다. 실제 순차 문답이 추가되므로 지연이 같다고 보장하지 않는다.

2026-09-10 운영 이력 표본에서 최초 평가 5회, 최종 평가 6회의 출력 잘림 재호출을 확인했다. 당시 최초 평가 상한은 1,900~7,500, 최종 평가는 3,400~8,000이었다. 반복 중단의 직접 원인은 주로 후속 질문·소통 요약의 개념/직군/질문 ID 불일치와 필수 필드 누락이었다. 긴 ID의 중복 생성을 선택지 기반 서버 연결로 바꾸고, 검증 오류에 항목 위치·허용 ID를 포함했으며, 출력 여유와 부분 수리 보존을 함께 보완했다. 외부 서비스 장애나 실행 예산 소진까지 무제한 재시도로 숨기지는 않는다.

## 회귀 검증

```powershell
.venv/Scripts/python.exe -m pytest pilot/tests -q
```

관련 테스트는 `test_evaluation_meeting.py`, `test_meeting_validation.py`, `test_meeting_runtime.py`, `test_meeting_reliability.py`, `test_review_matrix.py`다. 유료 모델 호출을 차단한 환경에서 문답 단계 순서, 평가 반영, 참조 검증, 실패·재개, 순위 실패 시 후보 보존, 기존 저장 상태 호환성, 짧은 참조 선택지와 부분 수리를 검증한다.
